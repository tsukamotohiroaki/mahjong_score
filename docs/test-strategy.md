# テスト戦略

本プロジェクトの品質保証の全体像をまとめたドキュメント。
「どこに厚くテストを張り、どこを浅くし、なぜそう判断したか」を言語化する。
テスト構成に影響する変更（テストレイヤーの追加・急所の変化）をしたときは、このドキュメントも更新する。

※ 記載しているテストケース数は 2026年8月 時点の実測値。測定方法は末尾に記載。

## 品質保証の考え方

- 守る対象は機能ではなく体験。このアプリの体験の核は **「記録したスコアが正しい」** こと
- リスクは「起きる可能性 × 影響の大きさ × 受け入れ可否」で評価し、リスクの高い箇所に厚くテストを配分する
- 「気をつける」ではなく「気をつけなくても壊れない仕組み」で品質を守る（テスト・不変条件・依存マップ）

## 急所マップ

「ここが壊れたらアプリの価値がなくなる」箇所と、その理由。

### 急所① 順位点計算（`Game#calculate_ranking_scores`）

- **なぜ急所か**: このアプリの存在価値は「スコアが正しいこと」ただ一点。計算が狂えば、他がすべて動いていても価値がない
- **なぜテストでしか守れないか**: 計算バグは例外を投げず、**黙って間違った数字を出す**。クラッシュしないためユーザーも開発者も気づきにくく、手動テストや目視では検出が困難
- **特に危険なケース**: 同点時の順位点均等分配。端数が絡むエッジケースは手動で網羅できないため、同点パターンごとにテストを用意している

### 急所② データの不変条件（インバリアント）

壊れたデータをそもそもデータベースに入れないための防御線。

- **順位点のゼロサム検証**: 順位点の合計は「(返し点 − 持ち点) × 4 ÷ 1000」と一致しなければならない。ここが崩れるとゲーム全体の点数収支が合わなくなる
- **プレイヤー4人固定**: 順位点計算・ゼロサム検証は4人を前提にしているため、`Game.create_with_players!` でトランザクションを張り、4人ちょうどでなければ全体をロールバックする
- **なぜ急所か**: 不正なデータが一度入ると、その後のすべての計算・集計が汚染される。入口で止めるのが最も安いタイミング

### 急所③ 点数入力フロー

- **バリデーション**: 各プレイヤーの入力は百点単位で ±1000（±10万点）の範囲内、4人の合計は 1000（10万点）ちょうど
- **なぜ急所か**: ユーザーが毎回通る導線であり、不正値の唯一の入口。入力補助の JavaScript（リアルタイム合計・4人目自動補完・送信ボタン制御）はサーバー側テストでは検証できない
- **防御構成**: クライアント側（Stimulus）の検証はあくまで UX 向上のため。**正であるのはサーバー側の検証**で、クライアント検証をすり抜けた値もサーバーで必ず拒否する（二重防御）

## テストの厚み配分（実測）

急所には厚く、単純な箇所は浅く。テストケース数の偏りは意図的なもの。

|---|---|---|---|
| 急所① 順位点計算・急所② 不変条件 | `spec/models/game_spec.rb` | 21 | 同点分配・境界値（3人/5人/0人/配列以外）を個別に検証 |
| 急所③ 点数入力（MPA版） | `spec/requests/rounds_spec.rb` | 16 | バリデーション・保存・上書き・採番を網羅 |
| 急所③ 点数入力（API版） | `spec/requests/api/v1/rounds_spec.rb` | 7 | MPA版と同一仕様の契約を検証 |
| 急所③ 点数入力の JS 挙動 | `e2e/score_input.spec.ts` | 8 | リアルタイム合計・自動補完・送信ボタン制御はブラウザでしか検証できない |
| ゲーム作成・一覧画面 | `spec/requests/games_spec.rb` | 28 | 画面表示とゲーム作成（4人検証含む）の入出力 |

## テストレイヤーの役割分担

| レイヤー | ツール | 守るもの | 例え |
|---|---|---|---|
| 単体（モデル） | RSpec | 計算ロジック・不変条件 | 厨房の裏側を守る門番 |
| リクエスト | RSpec | HTTP 入出力・バリデーション・ステータスコード | 注文の受け渡しを守る門番 |
| E2E（End-to-End） | Playwright | JavaScript の挙動・ユーザー操作フロー | お客さんの席を守る門番 |

### E2E を薄く保つ理由

- E2E は遅く、フレイキー（不安定）になりやすい。増やすほど CI の信頼性と速度が落ちる
- バリデーションの組み合わせ検証はリクエストスペックで済むため、E2E には**ブラウザでしか検証できないもの**（JavaScript の挙動、画面遷移フロー）だけを置く
- 導入タイミングも戦略的に選んだ: インライン JavaScript を Stimulus へリファクタリングする前に、現在の動作を E2E で固定してから書き換える（リファクタリングの安全網として導入）

## テスト以外の堅牢化の工夫

テストは防御線のひとつでしかない。壊れにくくする仕組みを重ねている。

- **トランザクション**: ゲーム＋プレイヤー4人の作成、ラウンド＋スコア4件の保存は、すべて成功するか、すべてロールバックするかの二択にする（中途半端なデータを残さない）
- **二重実装マップ**（`docs/architecture.md`）: MPA 版と LIFF 版で「同一仕様の別実装」になっているペアを一覧化し、仕様変更時に片方だけ直して仕様が乖離する事故を防ぐ
- **OpenAPI 仕様書**（`docs/openapi.yaml`）: MPA 版と LIFF 版の橋渡しをする JSON API の契約を明文化する
- **依存マップ**（`.claude/dependencies.md`）: ソースコードとテストの依存関係を記載し、AI エージェントとの協働開発でコード変更前に影響範囲を把握する（TDAD: Test-Driven Agentic Development）
- **TDD（テスト駆動開発）**: テストを先に書き、失敗を確認してから実装する。Red → Green → Refactor

## やらないと決めたこと

限られたリソースをリスクの高い箇所に集中させるため、以下は意図的にやらない。

- **E2E での網羅的なバリデーション検証**: リクエストスペックで担保済み。E2E で重複させるとコストだけ増える
- **カバレッジ100%の追求**: カバレッジは結果指標であり目的ではない。急所の網羅を優先する
- **周辺モデルへの深いテスト**: 単純なバリデーションのみのモデル（Player / Round / Score）は浅いテストで十分
- **当面スコープ外**: 負荷テスト・セキュリティテスト・ビジュアルリグレッションテストは MVP フェーズでは実施しない（ユーザー数・データ量が小さくリスクが低いため。本格運用フェーズで再評価する）

## テストケース数の測定方法

このドキュメントの数字は以下で再測定できる。

```bash
# RSpec のケース数（ファイルごと）
grep -rcE '^\s*it\b' spec/models/ spec/requests/

# E2E のケース数
grep -c "test(" e2e/*.spec.ts
```
