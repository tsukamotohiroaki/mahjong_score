# ADR-0001: MPA 版を撤去せず、LIFF 版と並ぶ正式なクライアントとして維持する

- ステータス: 決定
- 決定日: 2026-08-22
- 関連: [#271](https://github.com/tsukamotohiroaki/mahjong_score/issues/271) / [#175](https://github.com/tsukamotohiroaki/mahjong_score/issues/175) / [#268](https://github.com/tsukamotohiroaki/mahjong_score/issues/268)

## 背景

当初の方針は、MPA 版（Rails + ERB + Hotwire）で MVP を最短リリースし、動かしたまま LIFF 版（Next.js）へ段階的に移行して最終的に MPA を引退させる、というものだった（ストラングラーフィグパターン）。

その後、次の状態に至った。

- MPA 版・LIFF 版ともに主要フロー（ゲーム作成・点数入力・スコア一覧・共有）を実装済み
- 順位点計算とデータ保存は `Game` モデルと `RoundScoreForm` に集約され、両版で共有されている
- 一方で画面まわりは二重実装のまま（`score_input_controller.js` と `lib/score-input.ts` など）

ここで「移行の最終段階（MPA 撤去）を実行するか」を判断する必要が生じた。

## 決定

**MPA 版を撤去しない。** LIFF 版と並ぶ正式なクライアントとして維持する。

ストラングラーフィグパターンの Transform / Coexist は完了とみなし、**Eliminate（旧の撤去）は実行しない**。構成の呼称を「移行途中」から「マルチクライアント構成」に改める。

## 理由

### LINE プラットフォームを単一障害点にしない

LIFF 版のトップ（`frontend/app/page.tsx`）は `liff.login()` を通るため、LINE アカウントを持たない利用者はアプリに入れない。MPA を撤去すると、次がすべてアプリ全体の停止に直結する。

- LINE 側の障害
- LIFF の仕様変更・提供終了
- 利用者が LINE アカウントを持っていない

このアプリの本質は「麻雀のスコアを記録すること」であり、LINE は配布経路にすぎない。経路の可用性に本体の可用性を従属させない。

## 検討した選択肢

| 選択肢 | 内容 | 判断 |
|---|---|---|
| A. 撤去する | LIFF 版に一本化し、二重実装を解消する | **却下**。上記の理由による |
| B. 維持する | 両方を正式なクライアントとして扱う | **採用** |
| C. 役割を分ける | MPA を閲覧専用にし、入力は LIFF に寄せる | **保留**。二重実装の主要因（点数入力ロジック）は解消できるが、ブラウザだけで新規入力ができなくなる。将来の選択肢として残す |

## 結果

### 引き受けるコスト

二重実装（下記）は「移行完了までの一時的な負債」ではなく、**恒久的な管理対象**になる。

| 仕様 | MPA 版 | LIFF 版 |
|---|---|---|
| 点数入力の合計計算・自動補完 | `app/javascript/controllers/score_input_controller.js` | `frontend/app/lib/score-input.ts` |
| スコア一覧の表示（12局固定） | `app/views/games/show.html.erb` | `frontend/app/games/[id]/page.tsx` |

現状これらのテストは実装ごとに分かれており（Playwright は MPA、Vitest は LIFF）、**「2つが同一の挙動か」を検証する手段が存在しない**。片方だけを修正しても双方のテストが緑のまま通過してしまう。

### 必要になる対応

二重実装の一貫性は、人の注意力ではなく仕組みで担保する。

**1. 同じ spec ファイルを2つの入口に流す**（[#175](https://github.com/tsukamotohiroaki/mahjong_score/issues/175)）

同じ内容のテストを2本書くのではない。**1本の spec を `baseURL` 違いの2プロジェクトで実行する。**

```
e2e/score_input.spec.ts ─┬─→ baseURL :3000（MPA / Rails）      緑
                         └─→ baseURL :3001（LIFF / Next.js）   赤 ← 片方だけ直し忘れると落ちる
```

テストを2本用意すると、片方だけを修正して双方が緑のまま通過するという現状の問題をそのまま再現してしまう。**テストが1本しかないからこそ、実装の食い違いが必ず表面化する。**

**2. その結果をマージ条件にする**

どちらか一方のプロジェクトでも落ちればマージできない状態にする。検知する仕組みがあっても強制力がなければ、「赤いままマージ」で同じ事故が起きる。

**3. 自動化できない範囲に手動確認を限定する**（[#268](https://github.com/tsukamotohiroaki/mahjong_score/issues/268)）

見た目、および実機の LINE アプリ内でしか起きないこと（共有シート・テンキー・LIFF 起動導線）。

### LIFF 版の自動テスト可否（前提の確認）

「LIFF 版は自動テストが難しいから MPA を残す」という理由は成り立たない。LIFF SDK に依存するのは `/`（`frontend/app/page.tsx`）のみで、`/games/new` 以降の3画面は SDK を import しておらず、モックなしでそのまま E2E を実行できる。

`/` の役割は LIFF 初期化とログイン誘導、および `/games/new` へのリダイレクトのみで、アプリ機能を持たない。かつ `frontend/app/page.test.tsx` が `vi.mock("@line/liff")` で挙動を検証済みである。したがって `/` を E2E の対象外とすることに実質的な穴はない。

なお [#175](https://github.com/tsukamotohiroaki/mahjong_score/issues/175) が想定する「`page.addInitScript()` で `window.liff` を注入する」手法は、`page.tsx` が `import liff from "@line/liff"` でバンドル済みモジュールを参照しているため機能しない。同イシューは前提から見直す必要がある。

### 方針が変わる条件

次のいずれかが成立した場合、この決定を再検討する。

- 二重実装の一貫性を担保するコストが、ブラウザ経路を維持する価値を上回ったとき
- ブラウザ経由の利用実績が、維持コストに見合わないと判断できたとき
